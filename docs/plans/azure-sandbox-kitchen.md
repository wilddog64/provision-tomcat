# Azure Sandbox Test Kitchen Plan

## Goal
Enable the `provision-tomcat` role to run Test Kitchen suites against Windows and Linux hosts that live inside an A Cloud Guru (Pluralsight Skills) Azure sandbox instead of locally managed VirtualBox VMs. The end result should let contributors authenticate with `az login` and run `kitchen test` using Sandbox resources/quotas while keeping feature parity with the current Vagrant workflows.

## Constraints & Assumptions
- Sandbox sessions last four hours and expose a single pre-created subscription + resource group; plan must consume only those resources.
- Sandbox validation runs are **manual** for now: engineers start the sandbox, export env vars, and run Kitchen locally (e.g., from a GitHub runner on a Mac). CI wiring can be reconsidered later but is out of scope for this initial effort.
- Network egress is allowed, but inbound ports must be opened explicitly via NSGs. We still need HTTP (8080) and optional candidate port 9080 reachable from the Kitchen controller.
- Azure Sandbox quotas are small (≤10 vCPUs, basic SKU availability); choose VM SKUs (e.g., `Standard_B2ms`) and OS images the sandbox allows.
- We cannot create new resource groups; all infra must reuse the sandbox defaults.
- Developers will continue to run Ansible from their workstation; no changes to playbooks should be required beyond variable adjustments.

## Deliverables
1. `.kitchen.azure.yml` (or similar) with AzureRM driver configuration for Ubuntu 24.04, Rocky Linux 9, and Windows 11 test instances.
2. Updated `Gemfile`/docs describing additional Ruby dependencies (e.g., `kitchen-azurerm`).
3. Makefile targets/env-var workflow that simplifies switching between Vagrant and Azure configs.
4. Documentation updates (README + docs/TEST-KITCHEN.md) covering sandbox login, required env vars, and cleanup.
5. Smoke-tested instructions verifying a `kitchen test default-win11` style run completes in the sandbox.

## Work Plan

### 1. Capture Sandbox Inputs & Auth Flow
- Add a "Sandbox prerequisites" section to `docs/TEST-KITCHEN.md` describing how to start the Azure sandbox, copy the subscription ID, tenant ID, resource group, VNet/subnet names, and admin credentials.
- Document the exact `az login --use-device-code` flow and any required Azure CLI version (`README.md`).
- Define environment variables (e.g., `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`, `AZURE_LOCATION`, `AZURE_SANDBOX_USERNAME`, `AZURE_SANDBOX_PASSWORD`) and note they come from the sandbox UI.

### 2. Add Azure Driver Dependencies
- Extend `Gemfile` with `kitchen-azurerm` (and related Azure SDK gems if required) so Bundler installs the Kitchen driver.
- Update onboarding docs (`docs/DEVELOPMENT-SETUP.md`) to include Azure CLI + Ruby gem installation instructions for the driver.

### 3. Create Azure-Specific Kitchen Config
- Create `.kitchen.azure.yml` that:
  - Uses the `azurerm` driver with credentials sourced from env vars/`~/.azure/credentials`.
  - Defines platforms for Ubuntu 24.04, Rocky Linux 9, and Windows 11 (pointing to Marketplace images supported in the sandbox).
  - Maps suites identical to `.kitchen.yml` so provisioning steps remain unchanged.
  - Opens NSG rules for ports 5985 (WinRM), 22 (SSH), 8080, and 9080 as needed via the driver’s `public_ip` and `nsg` settings.
- Consider whether we can inherit from `.kitchen.yml` via ERB includes or keep the file standalone; capture decision in the plan before implementation.

### 4. Parameterize WinRM/SSH Settings
- Replace the hard-coded `ansible_user`, `ansible_password`, and `ansible_host` entries used for Vagrant (`.kitchen.yml` Windows platforms) with ERB variables referencing Kitchen driver outputs (e.g., `state[:public_ipaddress]`).
- Ensure the Windows guest enables Basic WinRM auth over HTTP and opens port 5985. Add a provisioner/extension script via Azure custom data if the base image does not already expose it.
- Validate Linux platforms use SSH keys generated by Kitchen and that Ansible picks up those credentials automatically.

### 5. Wire Makefile Support
- Add env var gating in `Makefile` so setting `KITCHEN_YAML=.kitchen.azure.yml` (or running a new target like `make test-win11-azure`) uses the Azure config.
- Provide helper targets to export subscription/resource details (e.g., `make kitchen-login-azure` running `az account show`).
- Keep existing Vagrant targets untouched so local workflows continue to function.

### 6. Documentation & Examples
- Expand `README.md` and `docs/TEST-KITCHEN.md` with a dedicated "Running in Azure Sandbox" section that walks through:
  1. Starting the sandbox session.
  2. Logging in via Azure CLI.
  3. Exporting the required env vars.
  4. Manually running `bundle exec kitchen list` / `kitchen test default-win11` **from the developer workstation or macOS GitHub runner** (call out that the sandbox is not wired into Actions yet).
  5. Destroying instances (`kitchen destroy --all`) before the sandbox expires and capturing logs/artifacts for PR notes.
- Mention sandbox limitations (no custom resource groups, limited regions) and expected runtime/cost.

### 7. Validation Checklist
- Dry run `bundle exec kitchen list -c .kitchen.azure.yml` to confirm driver auth works.
- For each platform, run `kitchen create`, `kitchen converge`, and `kitchen verify` against the sandbox, noting any Azure policy errors.
- Update docs with troubleshooting tips (e.g., NSG ports, insufficient quota) based on findings.

### 8. Follow-Up Enhancements (Optional)
- Investigate using Kitchen’s `transport: ssh` to run commands via Azure Bastion if direct public IPs are blocked.
- Explore automating sandbox resource cleanup via `az group delete` when sessions end.
